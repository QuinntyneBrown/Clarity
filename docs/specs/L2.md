# L2 - Detailed Requirements

## L2-001: User Login with JWT Token
**Traces to:** L1-001

The system must authenticate users via username and password, returning a signed JWT token on success. The token must be stored client-side and included in all subsequent API requests as a Bearer token.

**Acceptance Criteria:**
1. Given valid username and password, when the user submits login credentials to POST `/api/v1.0/user/token`, then the system must return a JWT token with user claims.
2. Given invalid credentials, when the user submits login credentials, then the system must return a 401 Unauthorized response.
3. Given an expired or missing token, when the user attempts to access a protected endpoint, then the system must return a 401 Unauthorized response.
4. Given a valid token, when the user makes an API request with the Bearer token header, then the system must grant access to the requested resource.

---

## L2-002: Password Hashing
**Traces to:** L1-001

The system must hash all user passwords with a unique salt using PBKDF2 before storage. Plaintext passwords must never be persisted.

**Acceptance Criteria:**
1. Given a new user registration, when the password is stored, then the stored value must be a salted PBKDF2 hash, not plaintext.
2. Given a password change request, when the new password is saved, then it must be hashed with a new salt before persistence.

---

## L2-003: Login Route Protection
**Traces to:** L1-001

The frontend must redirect unauthenticated users to the login page and prevent access to protected routes without a valid session.

**Acceptance Criteria:**
1. Given an unauthenticated user, when they navigate to any protected route, then the system must redirect them to `/login`.
2. Given an authenticated user, when they navigate to `/login`, then the system must redirect them to the default board view.
3. Given an authenticated user whose token expires, when they make a request, then the system must redirect them to `/login`.

---

## L2-010: Privilege-Based Authorization
**Traces to:** L1-003

The system must enforce fine-grained access control using privileges that define access rights (None, Read, Write, Create, Delete) per aggregate. Privileges are assigned to roles, and roles are assigned to users.

**Acceptance Criteria:**
1. Given a user with a role that has Read privilege on the Ticket aggregate, when they attempt to read tickets, then access must be granted.
2. Given a user with a role that has None access on the Ticket aggregate, when they attempt to read tickets, then access must be denied with 403 Forbidden.
3. Given a user with Write but not Delete privilege on an aggregate, when they attempt to delete, then the request must be denied.

---

## L2-011: Board CRUD Operations
**Traces to:** L1-004

The system must support creating, reading, updating, and deleting Kanban boards. Each board has a name and an ordered set of board states (columns).

**Acceptance Criteria:**

3. Given a valid board ID, when a DELETE request is made, then the board and its states must be removed.

## L2-012: Board State Management
**Traces to:** L1-004

Each board must have configurable states (columns) with a type (Backlog, InProgress, Done) and a display order. Board states must be creatable and deletable independently.

2. Given multiple board states, when the board is displayed, then states must be ordered by their Order property.
3. Given a board state with associated tickets, when the state is deleted, then the system must handle ticket reassignment or prevent deletion.

## L2-053: Canadian-Centric Contact Address
**Traces to:** L1-019

A contact must support multiple addresses. Each address has a type (Home, Work, Mailing, Billing, Other), street line 1, optional street line 2, city, province/state, postal/ZIP code, and country (defaulted to "CA"). Canadian postal codes must validate against the format `A1A 1A1` (case-insensitive, optional space).

**Acceptance Criteria:**
1. Given a contact, when POST `/api/v1.0/contact/{id}/address` is called with valid Canadian address data (province from CA province enum, postal code matching `^[A-Za-z]\d[A-Za-z][ ]?\d[A-Za-z]\d$`), then the address must be created and associated with the contact.
2. Given a contact with multiple addresses, when the contact is retrieved, then all addresses must be returned with their type and ordering.
3. Given an address with country = "CA" and an invalid postal code, when submitted, then the API must return 400 Bad Request with a postal-code validation message.
4. Given an address with country != "CA", when submitted, then the postal code must be accepted in any non-empty format up to the configured length.
5. Given an existing address ID, when DELETE `/api/v1.0/contact/{id}/address/{addressId}` is called, then the address must be removed from the contact.
6. Given a contact form, when the user selects country = "Canada", then the province field must present a dropdown of Canadian provinces and territories (AB, BC, MB, NB, NL, NS, NT, NU, ON, PE, QC, SK, YT).

## L2-054: Contact Phone Numbers
**Traces to:** L1-019

A contact must support multiple phone numbers. Each phone number has a type (Cell, Home, Work, Fax, Other), the number itself stored in E.164 format, an optional extension, and an optional `IsPrimary` flag. At most one phone per contact may be marked primary.

**Acceptance Criteria:**
1. Given a contact, when POST `/api/v1.0/contact/{id}/phone` is called with a valid phone (type, number), then the phone must be created and associated with the contact.
2. Given a contact with multiple phones, when retrieved, then all phones must be returned with their type, number, extension, and primary flag.
3. Given a Canadian-formatted input like `(416) 555-1234`, when submitted, then the system must normalize and store it as `+14165551234`.
4. Given an attempt to mark a second phone as primary on a contact that already has a primary phone, when submitted, then the previously-primary phone must be unset so that exactly one primary phone remains.
5. Given an existing phone ID, when DELETE `/api/v1.0/contact/{id}/phone/{phoneId}` is called, then the phone must be removed.
6. Given a phone number that fails E.164 validation, when submitted, then the API must return 400 Bad Request.

## L2-055: Contact Email Addresses
**Traces to:** L1-019

A contact must support multiple email addresses. Each email has a type (Personal, Work, Other), the address itself, and an optional `IsPrimary` flag. At most one email per contact may be marked primary.

**Acceptance Criteria:**
1. Given a contact, when POST `/api/v1.0/contact/{id}/email` is called with a valid email, then the email must be created and associated with the contact.
2. Given an email value that fails RFC 5322 validation, when submitted, then the API must return 400 Bad Request.
3. Given a contact already with a primary email, when a new email is marked primary, then the previously-primary email must be unset so that exactly one primary email remains.
4. Given an existing email ID, when DELETE `/api/v1.0/contact/{id}/email/{emailId}` is called, then the email must be removed.

## L2-056: Contact Notes
**Traces to:** L1-019

A contact must support an ordered list of notes. Each note has HTML-formatted content (sanitized via the existing Html value object), a reference to the authoring team member, a creation timestamp, and an optional last-modified timestamp.

**Acceptance Criteria:**
1. Given a contact, when POST `/api/v1.0/contact/{id}/note` is called with note content, then a note must be created with the current authenticated team member as author and a creation timestamp.
2. Given an existing note, when PUT `/api/v1.0/contact/{contactId}/note/{noteId}` is called, then the content and last-modified timestamp must be updated.
3. Given a note authored by another user, when the current user lacks Write privilege on the Contact aggregate, then PUT and DELETE on that note must be rejected with 403 Forbidden.
4. Given a valid note ID, when DELETE `/api/v1.0/contact/{contactId}/note/{noteId}` is called, then the note must be removed.
5. Given a note with HTML containing `<script>` tags or event handlers, when saved, then dangerous content must be sanitized using the same Html value object rules as comments (L2-030).
6. Given a contact, when GET `/api/v1.0/contact/{id}/note` is called, then all notes must be returned ordered by creation timestamp descending, including author display name.

## L2-057: Contact Employer Associations
**Traces to:** L1-019

A contact must support zero or more employer associations. Each association references an Employer entity (managed by the system, with name, optional website, optional industry, and optional address) and has a job title, start date, optional end date, and an `IsCurrent` flag. A contact may have multiple current employers (e.g., concurrent contracts).

**Acceptance Criteria:**
1. Given an existing employer and a contact, when POST `/api/v1.0/contact/{id}/employment` is called with employer ID, job title, and start date, then a contact-employer association must be created.
2. Given a new employer name not in the catalog, when an employment is created with `EmployerName` instead of `EmployerId`, then a new Employer entity must be created and associated.
3. Given an employment with `IsCurrent = true`, when the end date is set, then `IsCurrent` must be automatically set to false.
4. Given an existing employment ID, when PUT `/api/v1.0/contact/{contactId}/employment/{employmentId}` is called, then the job title, dates, and current flag must be updated.
5. Given an existing employment ID, when DELETE `/api/v1.0/contact/{contactId}/employment/{employmentId}` is called, then the association must be removed without deleting the Employer record.
6. Given a contact, when retrieved, then all employments must be returned with employer details and ordered by start date descending.
7. Given a request to delete an Employer that is referenced by at least one contact employment, when submitted, then the API must return 409 Conflict.

## L2-058: Tag CRUD Operations
**Traces to:** L1-020

The system must support creating, reading, updating, and deleting tags. Each tag has a unique name (1-50 characters, case-insensitive uniqueness) and an optional description (up to 500 characters). Tags are global and managed by the system, not scoped to a single contact.

**Acceptance Criteria:**
1. Given valid tag data (name, optional description), when POST `/api/v1.0/tag` is called, then a new tag must be created with a generated TagId.
2. Given a tag name that already exists (case-insensitive), when create is called, then the API must return 409 Conflict with a duplicate-name message.
3. Given an existing tag, when PUT `/api/v1.0/tag` is called with updated name or description, then the tag must be updated and the change must propagate to all contacts that reference the tag.
4. Given a valid tag ID, when DELETE `/api/v1.0/tag/{id}` is called, then the tag must be removed and all contact-tag associations referencing it must be removed.
5. Given an authenticated request, when GET `/api/v1.0/tag/all` is called, then all tags must be returned ordered by name ascending.
6. Given a tag name longer than 50 characters or empty, when submitted, then the API must return 400 Bad Request.

## L2-059: Apply Tags to Contacts
**Traces to:** L1-020

A contact must support zero or more tags via a contact-tag join. Tags can be added to and removed from a contact independently.

**Acceptance Criteria:**
1. Given a contact and an existing tag, when POST `/api/v1.0/contact/{id}/tag/{tagId}` is called, then the tag must be associated with the contact.
2. Given a contact already associated with a tag, when the same association is added again, then the API must respond with 200 OK without creating a duplicate join row.
3. Given a contact and a tag association, when DELETE `/api/v1.0/contact/{id}/tag/{tagId}` is called, then the association must be removed without deleting the tag.
4. Given a contact, when retrieved, then all tags applied to the contact must be returned with id, name, and description.
5. Given a request to associate a tag that does not exist, when submitted, then the API must return 404 Not Found.
6. Given GET `/api/v1.0/contact/by-tag/{tagId}`, when called, then all contacts associated with that tag must be returned.

## L2-060: Contact Search and Filter
**Traces to:** L1-019

The system must provide search and filter capabilities for contacts by name, email, phone, employer, and tag.

**Acceptance Criteria:**
1. Given a query string, when GET `/api/v1.0/contact/search?q={query}` is called, then contacts matching by first name, last name, preferred name, primary email, or primary phone (substring, case-insensitive) must be returned.
2. Given one or more tag IDs, when GET `/api/v1.0/contact/search?tagIds={id1}&tagIds={id2}` is called, then only contacts associated with all specified tags must be returned (AND semantics).
3. Given an employer ID, when GET `/api/v1.0/contact/search?employerId={id}` is called, then only contacts with an employment referencing that employer must be returned.
4. Given a result set larger than the page size (default 50), when search is called without a `page` parameter, then the first page must be returned with a `totalCount` field for pagination.
5. Given the global search input (L2-034), when the user submits a query, then matching contacts must appear in the search results grouped under a "Contacts" section.

## L2-061: Contact List and Editor UI
**Traces to:** L1-019

The frontend must provide a contact list view at `/contacts` and a contact editor at `/contacts/{contactId}/edit` (with `/contacts/new` for creation). The editor must allow managing addresses, phones, emails, notes, employments, and tags inline.

**Acceptance Criteria:**
1. Given an authenticated user, when they navigate to `/contacts`, then a paginated list of contacts must be displayed with name, primary email, primary phone, current employer, and applied tags as columns.
2. Given the contact list, when the user types in a search input, then the list must filter using the search endpoint (L2-060) with debounced input.
3. Given the editor, when the user adds a phone, email, or address row, then the change must be saved on form submit (not per-row).
4. Given the editor, when the user clicks "Add Tag", then a typeahead must let them select an existing tag or create a new tag inline (creating a new tag calls L2-058 and then associates it via L2-059).
5. Given the editor, when the user clicks "Add Note", then a rich-text editor must allow HTML input, and on save the note must be persisted via L2-056.
6. Given a contact with employments, when the editor is displayed, then each employment must show employer name, job title, and dates with edit and delete affordances.
7. Given the user clicks delete on a contact, when they confirm, then the contact must be deleted via L2-052 and the user must be navigated back to `/contacts`.

## L2-062: Tag Management UI
**Traces to:** L1-020

The frontend must provide a tag management view at `/tags` for browsing, creating, editing, and deleting tags. This view must be available in both the main application and the admin application.

**Acceptance Criteria:**
1. Given an authenticated user with Read privilege on Tag, when they navigate to `/tags`, then all tags must be listed with name, description, and contact count.
2. Given the tag list, when the user clicks "New Tag", then a form must open allowing name and description entry; on save the tag must be persisted via L2-058.
3. Given an existing tag, when the user clicks edit, then the tag form must open pre-populated and on save must update the tag.
4. Given a tag with a non-zero contact count, when the user clicks delete, then a confirmation dialog must warn that all associations will be removed; on confirm the tag must be deleted via L2-058.

## L2-063: Contact and Tag Responsive UI
**Traces to:** L1-013

The contact list, contact editor, and tag management views must adapt to all supported viewport sizes.

**Acceptance Criteria:**
1. Given viewport width < 576px, when the contact list is displayed, then it must collapse into a single-column card layout showing name, primary contact info, and tags, hiding less important columns.
2. Given viewport width < 768px, when the contact editor is displayed, then sections (basic info, addresses, phones, emails, employments, tags, notes) must stack vertically with collapsible accordions.
3. Given viewport width >= 992px, when the contact editor is displayed, then it must use a two-column layout with basic info and tags on the left, related collections on the right.
4. Given viewport width < 576px, when adding a phone or address, then the type selector and inputs must be full-width and touch-friendly.

## L2-064: Contact and Tag Authorization
**Traces to:** L1-003

Contact, Employer, and Tag aggregates must integrate with the existing privilege-based authorization system. Each aggregate must have configurable Read, Write, Create, and Delete privileges.

**Acceptance Criteria:**
1. Given a user with a role that has Read privilege on the Contact aggregate, when they call any contact GET endpoint, then access must be granted.
2. Given a user with a role that has None access on the Contact aggregate, when they call any contact endpoint, then the request must be denied with 403 Forbidden.
3. Given a user with Write but not Delete privilege on Contact, when they attempt to delete a contact, then the request must be denied.
4. Given a user with Read on Contact but None on Tag, when they retrieve a contact, then tag associations must still be returned (read access on Contact implies read access on its child tag references for display), but the user must not be able to call `/api/v1.0/tag/all`.
5. Given a user without Create privilege on Tag, when they attempt the inline "create new tag" action in the contact editor (L2-061), then the action must be hidden in the UI and rejected by the API.

## L2-065: Contact Real-Time Updates
**Traces to:** L1-014

Connected SignalR clients must receive notifications when contacts, employments, notes, or tag associations change.

**Acceptance Criteria:**
1. Given a connected client viewing the contact list, when another user creates or updates a contact, then the list must update without a manual refresh.
2. Given a connected client viewing a contact editor, when another user adds a note, employment, or tag to the same contact, then the editor must surface the new data (or a non-destructive prompt to refresh if the user has unsaved edits).
3. Given a connected client, when a tag is renamed via L2-058, then the new name must propagate to all visible contact tag chips.

## L2-066: Contact Input Validation
**Traces to:** L1-018

All contact-related endpoints must validate input at the API boundary, including string length limits, format constraints, and referential integrity.

**Acceptance Criteria:**
1. Given a contact create request with first name or last name exceeding 100 characters, when submitted, then the API must return 400 Bad Request.
2. Given a date of birth in the future, when submitted, then the API must return 400 Bad Request.
3. Given an employment with start date later than end date, when submitted, then the API must return 400 Bad Request.
4. Given a request referencing a ContactId, EmployerId, or TagId that does not exist, when submitted, then the API must return 404 Not Found.
5. Given any string input on contact, employer, tag, address, phone, email, or note, when submitted, then it must be trimmed of leading/trailing whitespace and rejected if it contains null bytes or control characters (other than CR/LF in note HTML).

## L2-067: Contact Performance and Pagination
**Traces to:** L1-019

Contact list and search endpoints must remain performant as the contact count grows.

**Acceptance Criteria:**
1. Given a database with 10,000 contacts, when GET `/api/v1.0/contact/all` is called with default pagination (50 per page), then the p95 response time must be under 300 ms.
2. Given a search query, when GET `/api/v1.0/contact/search` is called, then the response must return within 500 ms p95 for a database of up to 100,000 contacts.
3. Given the contact list endpoint, when called, then it must support `page`, `pageSize` (max 200), and `sortBy` query parameters and return `totalCount`, `page`, and `pageSize` fields in the response envelope.
