# L2 - Detailed Requirements

## L2-001: User Login with JWT Token
**Traces to:** L1-001

The system must authenticate users via username and password, returning a signed JWT token on success. The token must be stored client-side and included in all subsequent API requests as a Bearer token.

**Acceptance Criteria:**
1. Given valid username and password, when the user submits login credentials to POST `/api/v1.0/user/token`, then the system must return a JWT token with user claims.
2. Given invalid credentials, when the user submits login credentials, then the system must return a 401 Unauthorized response.
3. Given an expired or missing token, when the user attempts to access a protected endpoint, then the system must return a 401 Unauthorized response.
4. Given a valid token, when the user makes an API request with the Bearer token header, then the system must grant access to the requested resource.

---

## L2-002: Password Hashing
**Traces to:** L1-001

The system must hash all user passwords with a unique salt using PBKDF2 before storage. Plaintext passwords must never be persisted.

**Acceptance Criteria:**
1. Given a new user registration, when the password is stored, then the stored value must be a salted PBKDF2 hash, not plaintext.
2. Given a password change request, when the new password is saved, then it must be hashed with a new salt before persistence.

---

## L2-003: Login Route Protection
**Traces to:** L1-001

The frontend must redirect unauthenticated users to the login page and prevent access to protected routes without a valid session.

**Acceptance Criteria:**
1. Given an unauthenticated user, when they navigate to any protected route, then the system must redirect them to `/login`.
2. Given an authenticated user, when they navigate to `/login`, then the system must redirect them to the default board view.
3. Given an authenticated user whose token expires, when they make a request, then the system must redirect them to `/login`.

---

## L2-004: Create User Account
**Traces to:** L1-002

The system must allow creation of user accounts with username, password, email, first name, last name, phone, job title, and avatar URL.

**Acceptance Criteria:**
1. Given valid user data, when a POST request is made to the user endpoint, then a new user account must be created and returned with a generated UserId.
2. Given a duplicate username, when a create request is made, then the system must reject the request with an appropriate error.

---

## L2-005: Update User Profile
**Traces to:** L1-002

The system must allow users to update their profile information including first name, last name, email, phone, job title, and avatar URL.

**Acceptance Criteria:**
1. Given an authenticated user, when they submit updated profile fields via PUT, then the profile must be persisted with the new values.
2. Given a request to update another user's profile without admin privileges, then the system must deny the request.

---

## L2-006: Change Password
**Traces to:** L1-002

The system must allow authenticated users to change their password via a dedicated endpoint.

**Acceptance Criteria:**
1. Given an authenticated user with a valid current password, when they submit a password change request, then the password must be updated with a new hash.
2. Given an incorrect current password, when the user submits a password change, then the system must reject the request.

---

## L2-007: List and Retrieve Users
**Traces to:** L1-002

The system must allow listing all users and retrieving individual users by ID.

**Acceptance Criteria:**
1. Given an authenticated request, when GET `/api/v1.0/user/all` is called, then the system must return all user accounts.
2. Given a valid user ID, when GET `/api/v1.0/user/{id}` is called, then the system must return that user's profile.
3. Given an invalid user ID, when a GET request is made, then the system must return a 404 Not Found.

---

## L2-008: Delete User
**Traces to:** L1-002

The system must allow deletion of user accounts by ID.

**Acceptance Criteria:**
1. Given a valid user ID and sufficient privileges, when a DELETE request is made, then the user account must be removed.
2. Given insufficient privileges, when a DELETE request is made, then the system must return a 403 Forbidden.

---

## L2-009: Role CRUD Operations
**Traces to:** L1-003

The system must support creating, reading, updating, and deleting roles. Each role has a name and a set of associated privileges.

**Acceptance Criteria:**
1. Given valid role data, when a POST request is made, then a new role must be created with a generated RoleId.
2. Given an existing role, when a PUT request is made with updated data, then the role must be updated.
3. Given a valid role ID, when a DELETE request is made, then the role must be removed.
4. Given an authenticated request, when roles are listed, then all roles with their privileges must be returned.

---

## L2-010: Privilege-Based Authorization
**Traces to:** L1-003

The system must enforce fine-grained access control using privileges that define access rights (None, Read, Write, Create, Delete) per aggregate. Privileges are assigned to roles, and roles are assigned to users.

**Acceptance Criteria:**
1. Given a user with a role that has Read privilege on the Ticket aggregate, when they attempt to read tickets, then access must be granted.
2. Given a user with a role that has None access on the Ticket aggregate, when they attempt to read tickets, then access must be denied with 403 Forbidden.
3. Given a user with Write but not Delete privilege on an aggregate, when they attempt to delete, then the request must be denied.

---

## L2-011: Board CRUD Operations
**Traces to:** L1-004

The system must support creating, reading, updating, and deleting Kanban boards. Each board has a name and an ordered set of board states (columns).

**Acceptance Criteria:**
1. Given valid board data, when a POST request is made, then a new board must be created with a generated BoardId.
2. Given an existing board, when a PUT request is made, then the board must be updated.
3. Given a valid board ID, when a DELETE request is made, then the board and its states must be removed.
4. Given a board name, when GET `/api/v1.0/board/name/{name}` is called, then the board must be returned.

---

## L2-012: Board State Management
**Traces to:** L1-004

Each board must have configurable states (columns) with a type (Backlog, InProgress, Done) and a display order. Board states must be creatable and deletable independently.

**Acceptance Criteria:**
1. Given a board, when a new board state is created with a StateType and Order, then it must appear as a column on the board.
2. Given multiple board states, when the board is displayed, then states must be ordered by their Order property.
3. Given a board state with associated tickets, when the state is deleted, then the system must handle ticket reassignment or prevent deletion.

---

## L2-013: Board Cloning
**Traces to:** L1-004

The system must allow cloning an existing board, creating a copy with the same states and configuration.

**Acceptance Criteria:**
1. Given an existing board, when POST `/api/v1.0/board/{id}/clone` is called, then a new board must be created with the same states and configuration as the original.
2. Given a cloned board, when it is retrieved, then it must have independent board states that do not affect the original.

---

## L2-014: Kanban Board Visualization
**Traces to:** L1-004

The frontend must display boards as a Kanban view with columns representing board states and tickets displayed as cards within their respective columns.

**Acceptance Criteria:**
1. Given a board with states and tickets, when the user navigates to `/kanban/{boardName}`, then the board must display columns for each state with tickets as cards.
2. Given a board with no tickets, when displayed, then empty columns must be shown with the ability to add tickets.
3. Given a board selection control, when the user switches boards, then the view must update to show the selected board's tickets and states.

---

## L2-015: Sticky Kanban Header
**Traces to:** L1-004

The Kanban board must have a sticky header that animates into view when the user scrolls down the board.

**Acceptance Criteria:**
1. Given the user is at the top of the Kanban board, when the header area is visible, then the sticky header must not be shown.
2. Given the user scrolls past the board header, when the header leaves the viewport, then a sticky header must animate in at the top of the screen.
3. Given the user scrolls back up, when the original header re-enters the viewport, then the sticky header must animate out.

---

## L2-016: Ticket CRUD Operations
**Traces to:** L1-005

The system must support creating, reading, updating, and deleting tickets. Each ticket must have a name and may have description, acceptance criteria, story points, effort, priority, ticket type (Story/Chore), and assigned team member.

**Acceptance Criteria:**
1. Given valid ticket data, when a POST request is made, then a new ticket must be created with a generated TicketId.
2. Given an existing ticket, when a PUT request is made, then all editable fields must be updated.
3. Given a valid ticket ID, when a DELETE request is made, then the ticket must be removed.
4. Given a ticket name, when GET `/api/v1.0/ticket/name/{name}` is called, then the matching ticket must be returned.

---

## L2-017: Ticket Upsert
**Traces to:** L1-005

The system must support an upsert operation that creates a ticket if it does not exist or updates it if it does.

**Acceptance Criteria:**
1. Given ticket data with no existing matching ticket, when PUT `/api/v1.0/ticket/upsert` is called, then a new ticket must be created.
2. Given ticket data matching an existing ticket, when the upsert endpoint is called, then the existing ticket must be updated.

---

## L2-018: Ticket Board Association
**Traces to:** L1-005

Tickets must be associated with board states via a TicketState join entity. Tickets can be retrieved by board ID or board name.

**Acceptance Criteria:**
1. Given a ticket assigned to a board state, when the board is displayed, then the ticket must appear in the correct column.
2. Given a board ID, when GET `/api/v1.0/ticket/board/{id}` is called, then all tickets on that board must be returned.
3. Given a board name, when GET `/api/v1.0/ticket/board/name/{name}` is called, then all tickets on that board must be returned.

---

---

**Acceptance Criteria:**

4. Given a delete operation, when a DELETE request is made, then the entity must be removed and a success response returned.

**Traces to:** L1-013

The frontend must use NgRx Component Store for reactive state management, with dedicated stores per domain area and view model composition for components.

**Acceptance Criteria:**
1. Given any domain entity (tickets, boards, initiatives, etc.), when CRUD operations occur, then the corresponding store must update its state reactively.
